# Проверка на симуляциях

Как узнать, что оценщик работает, если на реальных логах истинный ответ неизвестен? Нужно прогнать его на
данных, где истина известна точно, — много раз и в разных условиях.

[`examples/validate.py`](../examples/validate.py) делает это на синтетическом банке
[`ps.synthetic.OfferSimulator`](../src/policyscope/synthetic.py):

- четыре оффера, категориальный регион;
- две метрики: принятие (0/1) и выручка;
- по желанию — повторные визиты клиента с ненаблюдаемой склонностью соглашаться.

Истинное значение политики считается **аналитически**: вероятность принятия интегрируется по клиентскому
эффекту квадратурой Гаусса–Эрмита. Поэтому измеряемое смещение — это смещение оценщика, а не шум эталона.

```bash
python examples/validate.py --runs 60                    # все сценарии, ~20 минут
python examples/validate.py --runs 30 --strict           # с порогами приёмки (так запускается в CI)
```

## Сценарии

Во всех сценариях кандидат B — softmax-политика по другим скорам.

| Сценарий | Логирующая политика A | Пропенсити | Основной оценщик | Особенность |
|---|---|---|---|---|
| `logged` | ε-greedy, ε = 0.2 | в логах | DR | базовый случай |
| `softmax` | softmax, T = 2 | в логах | DR | умеренно тяжёлые веса |
| `weak_overlap` | softmax, T = 0.5 | в логах | DR | пропенсити до 1e-10: перекрытия почти нет |
| `estimated` | ε-greedy, ε = 0.2 | **не залогированы** | DR | модель пропенсити + bootstrap |
| `clustered` | ε-greedy, ε = 0.2 | в логах | DR | 5 визитов на клиента, клиентский эффект |
| `dm` | ε-greedy, ε = 0.2 | в логах | **DM** | явный выбор DM, bootstrap-интервал |
| `dm_pair2` | ε-greedy, ε = 0.2 (другие сиды: A3 → B5) | в логах | **DM** | пара, на которой выигрыш DM меньше |

## Как читать таблицу

Смещение, RMSE и покрытие считаются по прогонам, которые библиотека **не** пометила как «ненадёжно»: именно
в них пользователь делает вывод. Колонка «RMSE по всем прогонам» показывает, что было бы, если игнорировать
вердикт. Интервал у DM есть только в сценариях, где он основной; в остальных DM — точка для сверки.

Приёмка (`--strict`) проверяет основной оценщик сценария:

- смещение в пределах 3 MCSE;
- покрытие не ниже 0.90 с поправкой на погрешность Монте-Карло;
- в сценарии `weak_overlap` не меньше 30% прогонов помечены «ненадёжно».

## Выводы

1. **С логированными пропенсити DR несмещён, а 95% интервал покрывает истину в 87–100% прогонов**
   (`logged`, `softmax`, `clustered`, строки DR в `dm`/`dm_pair2`; MCSE покрытия — в таблице). SNDR ведёт
   себя так же; IPS шумнее.
2. **Вердикт доверия отделяет катастрофы от пригодных оценок.**
   - В `weak_overlap` RMSE(DR) по всем прогонам равен 12 на метрике, лежащей в [0, 1]: отдельные веса
     достигают миллиардов.
   - Библиотека помечает такие прогоны как ненадёжные (47%) и не выдаёт по ним вывода.
   - Среди остальных RMSE = 0.05, покрытие 0.97.
3. **Без логированных пропенсити оценка остаётся пригодной.** DR несмещён в пределах погрешности, покрытие
   bootstrap-интервала 0.93–0.97. IPS и SNIPS смещены, поэтому при оценённых пропенсити основным может быть
   только DR или SNDR.
4. **Кластерный интервал держит покрытие при повторных визитах.** О том, почему без кластеризации
   интервалы для `V(A)` и `V(B)` занижены, — в [методологии](methodology.md#4-доверительные-интервалы).
5. **DM точнее DR, когда модель исхода близка к верной, и его bootstrap-интервал честен.**
   - В сценариях `dm` и `dm_pair2` покрытие 0.97–1.00, смещение в пределах погрешности.
   - RMSE в 1.2–2.7 раза ниже, чем у DR.
   - Это верно для симулятора, где модель исхода почти верна. На реальных данных смещение DM по логам не
     проверяется, поэтому DM — явный выбор, а не значение по умолчанию. Разбор и цифры, где DM ломается,
     — в [estimators.md](estimators.md).
6. **Модель исхода для выручки — двухчастная.** Прежняя (Ridge с обрезкой прогнозов) смещала DM на
   несколько его стандартных ошибок на части пар политик. Сравнение моделей — в
   [estimators.md](estimators.md#что-изменено).

## Границы

- Синтетика проще реальности: нет дрейфа во времени, нет ненаблюдаемых конфаундеров, признаки известны.
  Проверка подтверждает, что методы реализованы верно и честно сообщают о проблемах. Она не гарантирует
  точность на любых данных.
- В сценариях с bootstrap 30 прогонов, поэтому погрешность покрытия там около ±0.03–0.06 (см. таблицу).
