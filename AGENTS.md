# AGENTS.md — долгоживущие правила для AI-агентов

Этот файл фиксирует **стабильные** правила проекта для любых будущих изменений.

## 1) Scope проекта (стабильный)

- Репозиторий — библиотека для **contextual bandit off-policy evaluation (OPE)**.
- Основной сценарий: по логам поведения политики **A** (behavior/logging policy) оценить кандидата **B** (target/candidate policy).
- Ключевые выходы: `policy value` и `policy value difference (delta)` с диагностикой и инференсом.
- Ключевые inferential outputs: доверительные интервалы (CI) и significance metadata (`p-value` или честное CI-based decision); основной сравнительный объект инференса — `delta = V_B - V_A`.

## 2) Терминология (использовать в коде/доках)

- Предпочитать формулировки:
  - behavior/logging policy A,
  - target/candidate policy B,
  - policy value,
  - policy value difference / delta.
- Термин `ATE` не использовать в публичных текстах без необходимости (допустим только для совместимости в legacy-коде/комментариях).

## 3) Архитектурные принципы

- Разделять слои:
  1. data contract и валидация данных,
  2. point estimators,
  3. inference (CI + p-values + metadata),
  4. diagnostics/reporting.
- Diagnostics обязательны рядом с инференсом, но не заменяют CI/p-value.
- Базовая абстракция награды — **скалярная** метрика; multi-metric сценарии моделируются как повторные оценки по нескольким scalar targets.
- Не менять математическую сущность уже реализованных оценщиков без явного запроса.
- Избегать неограниченного API-churn: изменения делать инкрементально и совместимо, где возможно.

### 3.1 Инварианты, которые нельзя нарушать

- **Формулы оценщиков живут в одном месте** — `estimators.estimator_contributions`.
  Точечная оценка и инференс обязаны брать значение оттуда, иначе они разойдутся.
  Инвариант: `mean(contributions) == значение оценки`.
- **Никаких молчаливых деградаций.** Если что-то подставляется вместо
  отсутствующих данных (пропенсити, действие вне носителя, откат к другому
  источнику), это обязано попадать в диагностику и в предупреждения. Молчаливая
  подстановка `eps` вместо пропенсити порождает веса порядка `1/eps`, которые
  в одиночку определяют результат.
- **Точечная оценка и её CI описывают один и тот же оценщик.** Если точечная
  оценка cross-fit, то и реплики bootstrap обязаны быть cross-fit.
- **Признаки не должны содержать награду, действие или пропенсити.** Автовыбор
  исключает фактические имена колонок, а не заранее зашитый список.
- **Тип модели определяется по данным**, а не по имени целевой колонки.
- **Схема результата стабильна**: поля присутствуют всегда, отсутствующие
  значения равны `None`.

## 4) Тестирование и проверка изменений

- Перед коммитом запускать релевантные автоматические проверки:
  - `pytest -m "not slow"` — обязательно;
  - `pytest -m slow` — при изменениях в оценщиках, nuisance или инференсе;
  - `flake8 src tests examples`.
- **Изменения в математике или инференсе обязаны сопровождаться тестом
  корректности**, а не smoke-тестом. Проверка «код не падает» ничего не
  доказывает: значение может быть произвольно неверным. Ориентир —
  `tests/test_estimator_correctness.py`: точные значения на ручном примере,
  тождества между оценщиками, несмещённость с негативным контролем.
- Для notebook/tutorial изменений: переисполнять только затронутые `.ipynb`.
- Не оставлять временные артефакты в diff (`__pycache__`, служебные файлы и т.п.).
- Не коммитить выводы ячеек ноутбука без необходимости: они дают огромный
  нечитаемый diff.

## 5) Ожидания к документации

- При изменении API/архитектуры/пользовательского workflow обновлять:
  - `README.md`,
  - профильные документы в `docs/`,
  - tutorial (если изменение влияет на пользовательский путь).
- Документация должна быть короткой, структурной и понятной для нового пользователя.

## 6) Анти-паттерны для Codex

- Не «зашивать» в правила жёсткие продуктовые решения, которые могут устареть (например, единственная обязательная форма high-level API).
- Не добавлять крупные зависимости без явной необходимости.
- Не смешивать в одном коммите несвязанные цели.
